# 0004. Every proposal must make a checkable prediction

**Status:** Accepted

## Context

In the original design, `RemediationProposal.expected_signal` was generated by the
model, emitted as an SSE payload field, and then never used. The Verifier judged
recovery from raw metrics and never saw what the proposing agent had predicted.

That leaves two failure modes invisible:

- **Unfalsifiable proposals.** "The service should improve" cannot be wrong, so it
  is never caught being wrong.
- **Unexplained recovery.** The service recovers, but not for the reason the agent
  believed. The outcome is good, the diagnosis is still wrong, and the fault will
  come back.

## Options

1. **Drop the field.** Honest, and gives up the mechanism.
2. **Keep generating it for display only.** What the original did: it looks like
   rigour without being it.
3. **Wire it into the Verifier and score against it.**

## Decision

Option 3.

- `expected_signal` is stored on `RemediationAction`, and the prompt requires it to
  name a metric and a threshold.
- `verifier.run()` receives the action and is required to return
  `expected_signal_met` plus a `signal_assessment` comparing prediction to
  observation.
- The two judgements are explicitly separated in the prompt: "is the service
  healthy?" and "did the predicted thing happen?" can disagree, and the
  disagreement is the information.
- When `recovered=true` but `expected_signal_met=false`, the loop emits a
  `guardrail` event flagging an unexplained recovery.
- `metrics.score_trajectory` scores `predictions_made` and `predictions_checked`.

## Consequences

**Good**

- Proposals become falsifiable, which is the precondition for any kind of learning.
- The coincidence case gets recorded instead of banked as a win.
- Vagueness is penalized where it happens, rather than surviving indefinitely.

**Bad**

- The Verifier's job is harder and its prompt is longer, which costs tokens on
  every iteration.
- A model that writes deliberately loose predictions ("metrics improve") can still
  satisfy `expected_signal_met` cheaply. The Critic is asked to object to exactly
  this, but nothing forces precision - it is a pressure, not a guarantee.
- One more field for a weak model to get wrong.
